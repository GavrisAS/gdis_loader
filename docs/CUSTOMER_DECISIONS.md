# Решения заказчика

Нормативные решения этой итерации собраны из `Вопросы_v1.1(1).xlsx` и
`Описание.txt`. Они имеют приоритет над ранними текстами проекта. Незакрытые
вопросы перечислены только в [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md).

## Рабочий scope и выбор месторождения

- `validate` обнаруживает canonical названия по текущему файлу фонда и показывает
  покрытие в ГДИ, ЛХА, базе истории и статусе исследований. Dropdown не строится
  из hardcoded списка.
- Один `update` формирует лист `Данные` только для одного явно выбранного
  месторождения. Если поле результата пусто, имя копии калькулятора получает
  суффикс `_UPDATED_<Месторождение>`; заданный пользователем путь сохраняется.
- Внутри выбранного месторождения в target попадают дающие, дающие газ и
  остановленные в отчетном периоде/месяце. `дающие` и `дающие газ` записываются
  как `Дающие газ`; остановленные записываются как
  `Остановленные в отчетном периоде`. Иные состояния исключаются.
- Не добавлять колонку месторождения в workbook.

## Идентичность, дата расчета и lifecycle

- Удалять только ведущие нули числовой части: `012 -> 12`, `092 -> 92`,
  `051_ЗБС -> 51_ЗБС`. Внутренние нули и suffix сохранять.
- `base_well_id` — физический корень только для поиска lineage; `target_well_id`
  сохраняет lifecycle suffix. Материнская, ЗБС, ПВЛГ/перевод и МЗС — разные
  истории. МЗС не схлопывать с материнской.
- После подтвержденного lifecycle boundary запись ГДИ/ЛХА/статуса без suffix
  можно отнести к этапу только при однозначных поле, физическом корне, точной
  дате, пласте и интервале истории. Не синтезировать suffix. Неполная дата,
  неразрешенная эквивалентность пласта и последовательные этапы без naming rule
  остаются ambiguous.
- `calculation_date` — локальная системная дата, полученная один раз в начале
  операции и переданная расчетам явно.
- `PartialDate` сохраняет DAY/MONTH/YEAR. День для MONTH/YEAR не придумывать;
  `Дата запуска` заполнять только при точности DAY.

## ГДИ и производные поля

- Валидными ГДИ являются записи вида `ИД`, `ИД+КВД` или `КВД`, включая
  поясняющие вариации. `Освоение`, отдельные `Pст` и `Pпл` исключаются.
  Глубина записи не является условием валидности.
- `ИД+КВД` считается одной записью в общем количестве и входит одновременно в
  группы ИД и КВД для продолжительности.
- `Количество ГДИ` — число валидных ГДИ текущей lifecycle-истории после запуска.
  При исследовании в том же MONTH/YEAR окне, что и неполная дата запуска,
  точное количество не угадывать. `Недостаточно ГДИС`: 0–1 — `Да`, 2+ — `Нет`;
  при неполной дате использовать definite/possible bounds и заполнять только,
  если threshold outcome однозначен.
- `Снижение продуктивности`: сравнить последние два валидных числовых
  коэффициента `a` текущей истории; `a_current > a_previous` — `Да`, иначе
  `Нет`. Если двух значений нет — blank с диагностикой.
- `Рост хлора`: `Cl_current > 2000` и одновременно
  `Cl_current - Cl_previous > 1000` — `Да`, иначе `Нет`. Cl измеряется в
  мг/дм3; равенство порогу не срабатывает. Если нет двух numeric values — blank.
- Для совпадающих метрики и timestamp в ЛХА выбирать максимум валидных numeric
  значений. После схлопывания определять current/previous; сохранять INFO и
  provenance выбранных исходных ячеек.
- `ЛНД = Да`, если reliability `Низкая` или RFP равно `нет`. `Нет` записывать,
  только если оба источника присутствуют и распознаны, а положительного условия
  нет; иначе blank.
- `Глубинные датчики` по последнему валидному ГДИ: numeric depth `>0` — `Да`,
  `0` — `Нет`, missing/invalid — blank. Это отдельный признак глубинности.
- `Продолжительность без ГДИ`: при наличии последнего валидного ГДИ считать
  `(calculation_date - latest_gdi_date).days / 365`; если ГДИ не было — считать
  от точной DAY launch date. Если launch MONTH/YEAR, оставить пустым.
- `Продолжительность без ИД` — от последнего ID/ID_KVD; `Продолжительность без
  КВД` — от последнего KVD/ID_KVD. Если соответствующего исследования не было,
  оставить blank до ответа v2.
- `Удельное количество ГДИ` при count > 0 и точной дате запуска:
  `((calculation_date - launch_date).days / 365) / count`. Сохранять полную
  точность float, записывать numeric Excel value. При нуле оставить поле пустым
  (`GDI_SPECIFIC_RATE_ZERO_COUNT`); для будущей формульной миграции `μi = 0` и
  скважина не входит в сигмоиду.
- До появления плана выполненных/планируемых работ для текущих target rows
  временно писать `ГТМ = Нет`.
- Средний `Дебит` — среднее по работающим дням; поле пока пусто до определения
  работающего дня.

## Статус исследований / ГДМ

- Читать листы `АР_таблица_БЛУ`, `АР_таблица_ПЛУ`, `АР_таблица_ХЛУ` общим reader
  по mapping кодов ЛУ. Для каждой строки хранить well/plast/type/date/Delta и
  provenance.
- Числовая строка с `abs(Delta) > 5` является кандидатом проблемы адаптации;
  `abs(Delta) <= 5` не является. `-`, пустое, Excel error и formula без cached
  numeric result не являются нулем.
- `Проблемы ГДМ` остается пустым до определения актуальной строки и fallback
  поведения (вопрос v2 №9). Отчет агрегирует количество прочитанных,
  numeric/invalid/missing строк и строк-кандидатов.

## Поля, ожидающие структурную миграцию

- `Расходомер`, `Последний АДД`, `Не проведен АДД` и `Техническая возможность`
  заказчик попросил исключить. Сейчас их target cells пусты. Столбцы,
  критерии, настройки и формулы не удалять в этой итерации.
- Не менять формулы, настройки, расчетные листы, charts и прочие части
  калькулятора. Writer меняет только XML листа `Данные` и `tblData`.

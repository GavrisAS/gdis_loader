# Решения заказчика

Документ фиксирует ответы из `Вопросы_v1.0.xlsx` и пояснение из `Описание.txt`. Презентация `Тестовый расчет рейтинга ГДИС19.03(1).pptx` не является источником бизнес-правил.

## CONFIRMED

### Scope и месторождение

- Рейтинг рассчитывается отдельно по каждому месторождению/лицензионному участку.
- В этой версии `target field = Береговое ЛУ`; reader истории использует лист `БЛУ`.
- Колонку `ЛУ`/`Месторождение` в калькулятор не добавлять. Другие участки остаются поддерживаемыми в модели данных.
- Состав строк Берегового фонда пока не выбран. Сохранять категории внутренне; отдельно отмечать eligibility `дающие`, `дающие газ`, `остановленные в отчетном периоде`. Не фильтровать строки таблицы по eligibility.

### Идентичность скважины

- Начальный ноль в числовом номере фонда незначащий: `012 -> 12`, `092 -> 92`.
- Нули внутри номера и буквенные/суффиксные части сохраняются.
- `physical_root` используется только для поиска связи между источниками. Целевая/lifecycle identity сохраняет суффикс: `51 != 51_ЗБС`, `54 != 54_ПВЛГ`, `10403 != 10403_МЗС`.
- `МЗС` — отдельная скважина и отдельная история; не схлопывать с материнской.
- Материнская скважина, ЗБС и ПВЛГ/перевод на пласт имеют отдельные истории. Неизвестные суффиксы сохраняются без автоматического удаления.
- Физический корень может помочь связать строки лишь при совпадении месторождения, пласта и однозначной временной/исторической привязке. Иначе связь остаётся неоднозначной.

### Дата расчета и история

- `calculation_date` — локальная системная дата, вычисляемая ровно один раз в начале validate/update и явно передаваемая всем временным вычислениям.
- Источник списка фонда — актуальный датированный файл фонда.
- Дата запуска означает начало добычи после бурения, подтвержденной ЗБС или подтвержденной ПВЛГ/перевода на другой пласт.
- `База по скважинам.xlsx` предназначена для просмотра истории, событий ГТМ, даты запуска и разделения историй после мероприятий.
- Даты истории хранят исходную точность `DAY`, `MONTH` или `YEAR`. Для месяца/года день не синтезируется; целевая дата запуска остаётся пустой с диагностикой.
- Подтвержденные lifecycle boundaries: ВНС, ЗБС, ПВЛГ/перевод. ПВР и КЛК пока только хранятся как события.

### ГДИ

- Для рейтинга классифицируются три группы: `ИД`, `ИД+КВД`, `КВД`.
- Текстовые вариации и пояснения сохраняются в raw source value и распознаются классификатором.
- `Освоение`, отдельные замеры `Pст` и `Pпл` не являются ГДИ.
- После даты запуска 0 или 1 валидное ГДИ означает срабатывание «Недостаточно ГДИС», 2 и более — не срабатывание. Определение «валидного ГДИ» ещё не завершено, поэтому target не заполняется.
- Для одной метрики ЛХА и одного timestamp среди валидных чисел выбирается максимум; current/previous вычисляются после схлопывания одинаковых timestamp. В отчёт добавляется INFO с provenance всех значений и выбранной ячейки.

### Подтвержденные целевые значения

- `ГТМ = Нет` для всех строк Берегового — временное решение до появления файла планируемых ГТМ.
- `ЛНД = Да`, если достоверность `Низкая` или выход на РФП равен `нет`; `Нет`, если оба распознаны и оба условия ложны; иначе пусто и diagnostic `LND_SOURCE_INCOMPLETE`.
- Для отдельной записи ГДИ `Глубина записи, м > 0` означает глубинное исследование. В поле `Глубинные датчики` для выбранного крайнего ГДИ: положительное значение — `Да`, явный ноль — `Нет`, пропуск/ошибка — пусто с diagnostic.
- Продолжительность без ГДИ при отсутствии ГДИ: `(calculation_date - launch_date).days / 365`; при наличии: `(calculation_date - last_gdi_date).days / 365`.
- Удельное количество ГДИ при `gdi_count > 0`: `((calculation_date - launch_date).days / 365) / gdi_count`.
- Средний дебит рассчитывается по работающим дням; точное определение работающего дня ещё не дано.

### Структура и безопасность

- Менять только лист `Данные` и связанный диапазон таблицы `tblData`; новые колонки не добавлять.
- Исходный калькулятор не перезаписывать. Writer сохраняет остальные ZIP/OOXML entries byte-identical.
- АДД и «Техническая возможность» заказчик попросил исключить. В этой итерации их листы/критерии и формулы не менять, целевые значения оставить пустыми. Статус: `TO_REMOVE_FROM_CALCULATOR_IN_SEPARATE_STRUCTURAL_MIGRATION`.

## PARTIALLY_CONFIRMED

- Правило количества «Недостаточно ГДИС» подтверждено, но состав «валидных» записей ожидает уточнения; нельзя выводить его из глубины записи.
- Формулы продолжительности без ГДИ и удельного количества подтверждены. Их target fields пока блокируются, когда дата запуска имеет неполную точность или набор валидных ГДИ не установлен.
- Для нулевого количества ГДИ подтверждено `μi = 0`, но значение исходного поля `Удельное количество ГДИ` не согласовано.
- ЛНД использует консервативный tri-state при пропусках. Заказчик ещё не утвердил бизнес-трактовку пропусков исходных полей.
- База истории описывает выполненные ЗБС/ПВЛГ; файла запланированных ГТМ пока нет. Поэтому `ГТМ = Нет` — временное решение, которое нужно заменить при появлении расписания.

## Техническая реализация

Reader новой базы автоматически находит двухстрочный заголовок и блоки `ГТМn`, хранит raw values и ячейки provenance. Поддерживаемое отображение листов: `БЛУ -> Береговое`, `ХЛУ -> Хадырьяхинское`, `ПЛУ -> Пырейное`; сейчас читается только лист целевого scope `БЛУ`.

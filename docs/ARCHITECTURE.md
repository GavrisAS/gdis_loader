# Архитектура gdis_loader

## Цель и ограничения

Загрузчик читает фонд, базу истории скважин, сводную ГДИ, ЛХА и схему суточного рапорта. Он записывает только лист `Данные` и диапазон `tblData` в копию существующего калькулятора. Правила заказчика и их статус собраны в [`CUSTOMER_DECISIONS.md`](CUSTOMER_DECISIONS.md); ожидания заказчика — в [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md).

Источники бизнес-правил: прямые ответы заказчика в `Вопросы_v1.0.xlsx`, `Описание.txt`, новый источник `База по скважинам.xlsx`, текущий калькулятор, исходный README и остальные актуальные исходные файлы. Презентация `Тестовый расчет рейтинга ГДИС19.03(1).pptx` не задаёт бизнес-правила.

## Поток данных

```text
Фонд ─────────────┐
История скважины ─┤
ГДИ ──────────────┼─> readers -> typed domain -> normalization -> lifecycle matching
ЛХА ──────────────┤                                           -> transforms -> diagnostics
Суточный рапорт ──┘                                                   |
                                                                      v
                                        OOXML patch: только Data worksheet + tblData
```

### Readers и domain

- `readers` читают конкретные Excel/XLSM схемы, сохраняют raw values и точные `SourceLocation(file, sheet, cell)`. Макросы не запускаются, источники не сохраняются.
- `База по скважинам.xlsx` имеет два ряда заголовков; блоки `ГТМn` находятся по шаблону заголовков, а не по фиксированным номерам блоков. Для target scope читается `БЛУ`; mapping поддерживает `ХЛУ` и `ПЛУ`.
- `PartialDate` сохраняет точность `DAY`, `MONTH` или `YEAR`. Синтетический день не создаётся.
- GDI raw type сохраняется рядом с `GdiKind`; `UNKNOWN` получает компактную INFO диагностику и не считается ГДИ.

### Identity и lifecycle matching

`base_well_id` — физический корень для поиска lineage. `target_well_id` — полная lifecycle identity. Числовые ведущие нули удаляются, suffix сохраняется: `51`, `51_ЗБС`, `54_ПВЛГ`, `10403_МЗС`. `МЗС` не схлопывается с материнской скважиной; неизвестные suffix сохраняются.

GDI matching использует exact identity. Если фонд содержит только физический root, суффиксная GDI identity рассматривается только с подтвержденной исторической границей, совпадающими полем/пластом и однозначной датой. LHA без suffix привязывается к суффиксному target только при совпадении поля, пласта и подтверждённого lifecycle интервала. Невозможность установить порядок для неполной даты даёт ambiguity с provenance.

Подтвержденные lifecycle boundaries: ВНС, ЗБС, ПВЛГ/перевод. ПВР/КЛК хранятся как события. Несколько последовательных ЗБС остаются неоднозначными до ответа о правилах именования.

### Transforms и target scope

Service вычисляет системную локальную `calculation_date` один раз в начале каждой операции; функции получают дату параметром. В этой версии target scope — Береговое. Категории фонда сохраняются; eligibility рассчитывается отдельно и не фильтрует target rows.

Сейчас target могут заполняться: `Скважина`, `Пласт`, `Дата запуска` (только точность DAY), `Глубинные датчики` для выбранной записи ГДИ, `ГТМ` (временно `Нет`), `ЛНД` по tri-state правилу, текущие/предыдущие Cl и ВГФ. Остальные поля остаются пустыми. Формулы, критерии и остальные листы калькулятора не меняются.

LND: `Низкая` reliability или распознанное `нет` для РФП дают Да; оба значения распознаны без положительного условия — Нет; иначе blank + diagnostic. Глубинное исследование — свойство одной GDI записи, глубина >0. Оно не является правилом валидности GDI.

LHA значения для каждой метрики отдельно схлопываются по timestamp в максимум валидных чисел; current/previous выбираются после collapse. Дубли разрешаются детерминированно независимо от порядка строк, с INFO provenance всех ячеек и выбранной ячейки.

Pure helpers покрывают количество недостаточных ГДИ, длительность без ГДИ и удельное число ГДИ; target fields заблокированы до согласования валидности и точности входов.

### Safe workbook writing

Writer читает заголовки/схему через `openpyxl`, затем копирует исходный ZIP и патчит только XML листа `Данные` и `tblData`. Он не выполняет openpyxl save round-trip. Нетаргетные ZIP entries должны оставаться byte-identical; namespace `x14ac` и правила условного форматирования сохраняются. Расширение диапазона таблицы не затрагивает другие листы.

### GUI, config и CLI

GUI использует PySide6-Essentials, worker thread и безопасные progress checkpoints. Путь к новой базе истории сохраняется в `config.toml`. В frozen сборке конфиг лежит рядом с EXE, в разработке — в корне репозитория. CLI `validate` и `update` принимают `--well-history` и используют тот же application service.

### Diagnostics и отчёт

Каждый запуск создаёт JSON и текстовый лог. Источниковые warning/error содержат точные locations, INFO по возможности тоже. В отчёте есть scope, eligibility, типы ГДИ, история/precision, LHA availability/duplicates, lifecycle gaps и итоговые строки. Не включать production row dumps.

### Проверка и Windows release

Обычный `make check` выполняет ruff lint, формат, ty и pytest. CI проходит на Linux и Windows. Push в `main` запускает Windows build/release workflow: PyInstaller `onedir`, frozen smoke-test, tag формата `vMAJOR.MINOR` на `github.sha` и GitHub Release только после успешной сборки. `workflow_dispatch` делает non-release artifact.

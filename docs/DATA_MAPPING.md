# Маппинг листа `Данные` — состояние первой версии

## Источник бизнес-правил

Решения для загрузчика принимаются только по текущему калькулятору
`GDIS_Rating_Calculator_FIXED.xlsx`, исходному `README.txt` и актуальным файлам
фонда, сводной ГДИ, ЛХА и суточного рапорта. Презентации, старый калькулятор,
DOCX и другие исторические материалы не являются источниками бизнес-правил без
отдельного запроса пользователя.

Статусы:

- `READY` — источник и правило достаточно определены для реализации;
- `CONDITIONAL` — можно заполнять только после однозначного well/plast match;
- `BLOCKED` — требуется уточнение бизнес-правила/источника.

## Реализованный алгоритм текущего базового scope

1. Фонд выбирает самый поздний лист с именем `DD.MM.YYYY`, исключая `RSPN`.
   В мастер-список входят C/D/G/H. Записи J (`в освоении / ожидании освоения`)
   исключаются по подтвержденному исходным README правилу действующий +
   бездействующий фонд и создают только INFO `FUND_CATEGORY_J_IGNORED` с
   provenance. Контрольные количества сравниваются с числом распознанных
   элементов.
2. Номер скважины нормализуется отдельно от исходного отображаемого имени:
   для matching числовые ведущие нули удаляются, но правило их сохранения в
   отображаемом поле пока не утверждено. Подтверждённые источниками маркеры
   `ЗБС`, `ГС` (а также явно поддержанные `ПВЛГ`/`КЛК`) обрабатываются
   консервативно; `МЗС` временно поддерживается для совместимости и не считается
   подтвержденным правилом. Неизвестный текстовый суффикс не удаляется.
3. ГДИ индексируется по `base_well_id`; далее применяются явный алиас поля,
   точный пластовый hint фонда при наличии и последняя дата не позднее даты
   фонда. Равные несовместимые кандидаты получают `AMBIGUOUS`.
4. ЛХА индексируется по номеру, полю и нормализованному пласту. Для каждого
   показателя отдельно строятся точки по **различным timestamp**; `0` валиден,
   Excel errors и нечисловые значения пропускаются. Повтор одного timestamp с
   одинаковым числом схлопывается. Различные значения в один timestamp не
   угадываются: выдаётся `LHA_DUPLICATE_TIMESTAMP_CONFLICT`, а конфликтная
   current/previous точка оставляется пустой без перехода к более старой точке.
   `Рост хлора` не считается.
5. Суточный рапорт на текущем базовом scope проверяется только по наличию файла, листа
   `Добыча телеметрия` и базовых заголовков `ГСК`/`СКВ.`. Полный reader дневных
   значений остаётся отдельным и покрытым тестами, но runtime pipeline его пока
   не вызывает: правило агрегации в `Дебит` не утверждено.

6. Диагностика разделяет источник на `ERROR` (операция невозможна), `WARNING`
   (проблема влияет на текущий фонд/целевое поле) и `INFO` (ожидаемый placeholder,
   служебный пропуск или историческая проблема, не влияющая на current/previous).
   Строки ГДИ и ЛХА, в которых пусты все четыре идентификационных поля записи,
   пропускаются даже при наличии значения в другой колонке. Частично заполненные
   строки по-прежнему получают консервативные `GDI_INVALID_*`/`LHA_INVALID_*`
   диагностики. `LHA_NOT_FOUND` добавляется только когда итоговые значения не
   выбраны и у `LhaSelection` нет собственного issue.
   В ЛХА конфликт одинакового timestamp получает WARNING только для первых двух
   выбираемых точек конкретной метрики; конфликт третьей или более старой точки
   не раздувает отчет.
7. После построения target rows loader группирует фактические целевые пары
   `Скважина + Пласт`. Если одна пара получена из разных `normalized_field`,
   добавляется WARNING `TARGET_IDENTITY_COLLISION` с fund/GDI provenance; сами
   целевые значения не изменяются, поскольку в калькуляторе нет отдельного поля
   месторождения.
8. Если актуальное сопоставление использует маркер `МЗС`, добавляется одна
   компактная диагностика `UNCONFIRMED_WELL_VARIANT_MZS` на target identity с
   provenance текущих fund/GDI строк. Исторические строки ГДИ отдельно не
   предупреждаются.
9. Сначала значения фонда разбираются только по подтвержденным разделителям
   (запятая, `;`, перевод строки). Numeric-whitespace-кандидат применяется
   только при известном контрольном количестве и только если после split число
   элементов точно совпадает с ним; иначе исходный токен сохраняется и
   формируется `FUND_COUNT_MISMATCH`. В текущем фонде `153 162` дает два номера
   при ожидаемом количестве 2 и сопровождается INFO
   `FUND_MISSING_SEPARATOR_NORMALIZED` с адресом исходной ячейки.

Последний шаг записи использует именованные заголовки листа `Данные`, а не
порядковые индексы. При сбое схемы или неоднозначном match результат не
подменяется догадкой: строка фонда сохраняется с явной диагностикой
`fund_fallback` только в поле `Скважина`.

## Минимальный полезный результат первой функциональной итерации

Первая версия должна прежде всего надежно построить мастер-список фонда и слой идентификации. После однозначного сопоставления разрешено записывать `Скважина`, `Пласт`, `Cl текущий`, `Cl предыдущий`, `ВГФ текущий`, `ВГФ предыдущий`.

Если статус `Состояние` не утвержден, строку все равно можно сформировать с пустым значением этого поля и диагностикой.

Наличие `BLOCKED`-полей не является ошибкой работы программы.

## Provenance диагностик

Readers сохраняют для identity/date/measurement-полей исходный файл, лист и
Excel-адрес. Warning/error diagnostics передают эти данные в immutable
`locations`; JSON хранит объекты `{file, sheet, cell}`, а текстовый лог выводит
те же адреса в форме `file::sheet::cell`. Для отсутствующего листа или другой
ошибки структуры, у которой нет физической ячейки, `cell` остаётся `null`.

Ты работаешь в репозитории `gdis_loader`. Это первый реализационный этап загрузчика данных для Excel-калькулятора рейтингования скважин ГДИС.

## 1. Цель итерации

Сделай первую реально запускаемую версию приложения с маленьким GUI, которая:

1. позволяет пользователю выбрать все входные файлы через диалоги;
2. запоминает выбранные пути в `config.toml` и восстанавливает их при следующем запуске;
3. валидирует структуру источников;
4. строит мастер-список эксплуатационного фонда;
5. реализует консервативное сопоставление скважины/актуального обозначения/пласта;
6. заполняет только однозначно определяемые на этом этапе поля листа `Данные`;
7. формирует копию калькулятора, не изменяя исходный файл;
8. формирует диагностический JSON + лог;
9. имеет unit/integration tests;
10. проходит `ruff`, `ty`, `pytest`;
11. собирается в Windows `onedir` через существующий workflow PyInstaller.

Не пытайся закончить всю предметную область за один шаг. Основная ценность этой версии — надежная инфраструктура, идентификация и отсутствие скрытых предположений.

- Excel COM, win32com, LibreOffice, VBA запрещены.
- Не модифицировать входные файлы.

## 6. Парсер фонда

Из `Фонд ...xlsx` не хардкодь конкретный лист `01.08.2026`.

Выбери наиболее поздний лист, имя которого после `strip()` строго соответствует `DD.MM.YYYY`. Листы `RSPN ...` не подходят.

Проверь, что дата в `C1` согласуется с именем листа; расхождение — warning/error с понятным сообщением.

Для текущей структуры эксплуатационный фонд в первой версии формируй из списков:

- колонка C — действующий, дающие газ;
- колонка D — остановленные в отчетном месяце;
- колонка G — бездействующие текущего года;
- колонка H — бездействующие прошлых лет.

**Не включай J** (`в освоении/ожидании освоения`) до решения вопроса заказчиком.

Строки с количествами чередуются со строками списков. Нельзя полагаться только на конкретные номера строк: используй структуру/признаки и валидацию, но для текущего формата допустима аккуратная схема чтения пар «строка объекта / следующая строка списка».

Распарси списки скважин, учитывая:

- запятые;
- переводы строк;
- лишние пробелы;
- числовые Excel cells;
- ведущие нули (`011`);
- смешанные типы значений.

Для каждой скважины сохрани как минимум:

- исходное отображаемое значение;
- `base_well_id`;
- месторождение/ЛУ;
- объект группы фонда;
- исходную категорию состояния;
- дату фонда.

**Не принимай пока окончательное значение целевого поля `Состояние`**, так как это бизнес-вопрос. В target row оставляй `Состояние` пустым, но сохраняй source status в доменной модели и diagnostic report.

После парсинга проверь контрольные количества: число распарсенных элементов по каждой категории должно совпадать с указанными в строке количествами там, где такие количества присутствуют. Несовпадение — diagnostic error/warning, не молчать.

## 8. Нормализация номера скважины

Сделай отдельный модуль + тесты.

Нужна консервативная функция получения `base_well_id`.

Требования:

- `011` и числовое `11` должны давать один base id;
- строковые и числовые значения должны обрабатываться одинаково;
- пробелы/неразрывные пробелы нормализовать;
- регистр русских/латинских букв в служебных суффиксах нормализовать;
- варианты ЗБС/ПВЛГ/КЛК/ГС и реальные формы из файла сначала исследуй и покрой tests;
- не удаляй произвольный текст после `_` универсальным regex — можно слить разные реальные сущности;
- сохраняй исходное полное имя отдельно.

Сначала собери частотный список реальных вариантов имен из ГДИ и фонда (это можно сделать вспомогательным dev-скриптом или тестовой аналитикой), затем зафиксируй только подтвержденные правила.

Если встречается новый неизвестный формат, base id может остаться unresolved; это лучше ложного match.

## 9. Нормализация пластов

Создай чистую нормализацию обозначения пласта для сравнений, сохраняя исходную строку для отображения.

Минимум обработать:

- пробелы;
- дефисы;
- Unicode subscript digits (`ПК₁`);
- регистр;
- очевидные косметические различия `ПК1` / `ПК-1`.

Не объединяй разные объекты по слишком агрессивному правилу. Например, `ПК-19-2` и `ПК19-20` не должны схлопываться.

Тестами зафиксируй каждое правило.

## 10. Well matching

Это ключевой модуль первой версии.

Для каждой скважины фонда:

1. найти записи ГДИ с тем же `base_well_id`;
2. учитывать месторождение (с нормализацией названий: например `Береговой` в фонде и `Береговое` в ГДИ могут требовать явной таблицы безопасных алиасов, найденных из данных; не использовать fuzzy matching);
3. учитывать объект/пласт, где сопоставление действительно возможно;
4. использовать дату ГДИ для выбора актуальной конфигурации;
5. актуальное полное имя `Скважина` и `Пласт` брать из последней **однозначной** релевантной записи.

Не использовать fuzzy string similarity и «самый похожий» выбор.

Введи явный результат сопоставления, например enum/status:

- `MATCHED`;
- `NO_GDI`;
- `AMBIGUOUS`;
- `INVALID_SOURCE`.

Для `AMBIGUOUS` обязательно хранить кандидатов и объяснение.

Если две записи на максимальную дату имеют несовместимые разные completion/plast и нельзя доказать выбор — ambiguous.

Не считай факт отсутствия ГДИ программной ошибкой.

## 11. ЛХА

Лист: `БД Сибнефтегаз`.

Находи колонки по заголовкам:

- `Месторождение`;
- `Номер скважины`;
- `Пласт`;
- `Дата и время исследования`;
- `Данные ЛХА, CL-, мг/дм3`;
- `ВГФ, г/м3`.

Для каждой успешно сопоставленной актуальной скважины/пласта выбери:

- последнюю валидную точку Cl;
- предыдущую валидную точку Cl;
- последнюю валидную точку ВГФ;
- предыдущую валидную точку ВГФ.

При этом:

- связь выполняется по `base_well_id` + нормализованному пласту + временному контексту;
- в ЛХА может отсутствовать суффикс ЗБС/ГС;
- не используй измерение прежнего пласта только потому, что base well совпал;
- Excel errors, строки `#DIV/0!`, `#REF!`, пустые и нечисловые значения не являются валидными числовыми точками;
- `0` является валидным числом и не должен отбрасываться как falsy;
- даты сортировать как datetime, а не как строки.

Если для показателя есть только одна валидная точка — заполнить только `текущий`, `предыдущий` оставить пустым.

Не вычисляй `Рост хлора` в этой версии.

## 12. Суточный рапорт

Реализуй reader/validator для листа `Добыча телеметрия`, чтобы приложение уже умело подтвердить, что файл корректен и прочитать структуру.

Но поле `Дебит` пока **не заполняй**, потому что не утвержден способ агрегации дневных значений в одно число.

Reader должен корректно переживать `#REF!` и хранить валидные дневные значения для будущего шага.

## 13. Что писать в `Данные` в этой итерации

Для каждой скважины фонда создай строку целевой модели со всеми 26 именованными полями, но заполняй только подтвержденные поля.

### При `MATCHED`

Разрешено заполнить:

- `Скважина` — полное актуальное имя из последней однозначной записи ГДИ;
- `Пласт` — актуальный пласт из той же записи;
- `Cl текущий`;
- `Cl предыдущий`;
- `ВГФ текущий`;
- `ВГФ предыдущий`.

### При `NO_GDI` или `AMBIGUOUS`

Не придумывай актуальное имя/пласт из истории. Для сохранения строки фонда можно записать в `Скважина` исходное обозначение из фонда только если это явно помечено в диагностике как `fund_fallback`, а `Пласт` оставить пустым, если объект нельзя перевести в точный пласт без предположения.

### Поля, которые оставить пустыми

До следующих бизнес-решений не заполнять автоматически:

- `Состояние`;
- `Дата запуска`;
- `Количество ГДИ`;
- `Глубинные датчики`;
- `Расходомер`;
- `ГТМ`;
- `Недостаточно ГДИС`;
- `Снижение продуктивности`;
- `Рост хлора`;
- `Проблемы ГДМ`;
- `ЛНД`;
- `Последний АДД`;
- `Не проведен АДД`;
- `Продолжительность без ГДИ`;
- `Удельное количество ГДИ`;
- `Продолжительность без ИД`;
- `Продолжительность без КВД`;
- `Техническая возможность`;
- `Дебит`;
- `Manual μ`.

Не заполняй их значением `Нет` только чтобы калькулятор не ругался. Сейчас важнее корректность данных.

## 14. Безопасная запись калькулятора

Это отдельная важная задача.

Сначала создай исследовательский test/tool, который сравнивает OOXML package исходного калькулятора и обычного `openpyxl` round-trip. Уже известно, что стандартный save способен изменить много нетаргетных частей, удалить `calcChain.xml`, `sharedStrings.xml` и неподдерживаемые extensions.

Поэтому writer должен стремиться к следующему инварианту:

> Все ZIP entries калькулятора, кроме XML листа `Данные` и непосредственно связанного определения `tblData`, остаются байтово идентичными исходнику, если это технически возможно.

Реализуй безопасный подход. Предпочтительный вариант:

1. использовать openpyxl для чтения структуры целевого листа/таблицы и проверки заголовков;
2. скопировать исходный `.xlsx` как OOXML zip-package;
3. минимально изменить XML sheet `Данные`:
   - сохранить строки 1–6;
   - заменить/очистить data rows начиная с 7;
   - сохранить стили/тип ячеек в нужном формате;
   - корректно записать строки результата;
4. изменить ref `tblData` с `A6:Z106` на `A6:Z{6+n}`;
5. не перепаковывать содержимое других XML средствами openpyxl;
6. после записи открыть результат openpyxl в read-only режиме и проверить данные;
7. дополнительно сравнить ZIP entries и выдать ошибку теста при неожиданном изменении нетаргетных частей.

Если найдешь надежный способ добиться той же сохранности чистым openpyxl — можно использовать его, но докажи это тестом на реальном калькуляторе. Не игнорируй warning об unsupported conditional formatting extension.

При расширении более 100 строк копируй стиль/атрибуты шаблонной последней строки данных только на новые строки листа `Данные`. Другие листы не расширяй.

Если количество строк >100, добавь warning в отчет:

`DATA_ROWS_EXCEED_CALCULATOR_FORMULA_CAPACITY`.

Не пытайся исправить расчетные листы в этой задаче.

## 15. Отчет загрузки

Сделай typed report model и сохраняй JSON рядом с выходным xlsx, например:

`GDIS_Rating_Calculator_UPDATED.load-report.json`.

Минимальная структура:

- timestamp;
- версии приложения/Python;
- входные пути (можно полные локальные пути; это локальный отчет, но не логировать содержимое файлов);
- дата фонда;
- `fund_total`;
- `matched`;
- `no_gdi`;
- `ambiguous`;
- `with_lha_cl`;
- `with_lha_vgf`;
- `rows_written`;
- warnings;
- issues с кодом, well id и кратким сообщением;
- список полей, которые намеренно оставлены незаполненными в v0.1.

JSON должен быть UTF-8, `ensure_ascii=False`, удобный для чтения.

Лог — стандартный `logging`, rotating file handler не обязателен для v0.1, но файл должен создаваться рядом с config или output.

## 16. Тесты

Добавь достаточно unit tests. Не подменяй их одним E2E.

Обязательные тесты:

### config

- отсутствующий config;
- round-trip путей с кириллицей;
- атомарная запись;
- поврежденный TOML.

### fund parser

- выбор самого свежего `DD.MM.YYYY` sheet;
- игнорирование `RSPN ...`;
- парсинг списков с запятыми/newlines/числами;
- ведущие нули;
- сверка контрольного количества;
- категории C/D/G/H;
- J не включается.

### well id

Покрой реальными классами имен, которые найдешь в предоставленном файле. Минимум leading zero + ЗБС/ПВЛГ/КЛК, если они реально встречены.

### plast

- `ПК₁` == `ПК-1` для matching;
- пробелы;
- не схлопывать различающиеся объекты.

### matcher

- exact single match;
- latest date;
- same base well, old and new plast;
- ambiguous on same latest date;
- no GDI;
- different field must not match.

### LHA

- two valid measurements;
- one valid measurement;
- `0` preserved;
- `#DIV/0!` ignored;
- old plast measurement excluded;
- dates sort correctly.

### target writer

Создай синтетический workbook fixture с table `tblData` и несколькими нетаргетными sheets/formulas. Проверяй:

- headers are not hardcoded by column index;
- previous data cleared;
- rows written;
- table ref resized;
- >100 rows supported;
- non-target sheets unchanged;
- source file unchanged;
- output reopens.

Дополнительно integration test на реальном `data/GDIS_Rating_Calculator_FIXED.xlsx` должен запускаться только если файл присутствует; в CI без data — skip.

### GUI

Не надо тяжело тестировать пиксели. Вынеси логику модели/контроллера так, чтобы config и запуск service тестировались без реального mainloop. Один простой smoke test GUI допустим, если стабилен на CI; если headless Linux мешает — не заставляй CI поднимать X server ради tkinter.

## 17. CLI

Сделай CLI параллельно GUI, чтобы бизнес-логику можно было тестировать и использовать в CI без UI.

Например:

```bash
uv run gdis-loader-cli validate --calculator ... --fund ... --gdi ... --lha ... --daily-report ...
uv run gdis-loader-cli update --calculator ... --fund ... --gdi ... --lha ... --daily-report ... --output ...
```

Можно использовать только `argparse` из stdlib. Не добавляй Click/Typer без необходимости.

GUI и CLI должны вызывать один и тот же application service.

## 18. Производительность

Файлы ЛХА крупные. Не загружай заведомо лишние листы/ячейки в память.

- Используй `read_only=True` там, где это совместимо с задачей.
- Используй `data_only=True` для источников, где нужны cached numeric results формул.
- Не проходи миллион Excel rows только потому, что `max_row == 1048576` из-за форматирования. Реализуй разумное прекращение чтения по длительной серии пустых строк или другой надежный bound после исследования реального файла.
- Не используй повторное полное чтение одного и того же 60+ MB файла для каждого well.
- Один проход -> индекс in-memory по ключам.

Покрой это хотя бы простым integration benchmark/log timing, без преждевременной микрооптимизации.

## 22. Acceptance criteria

Задача считается завершенной, если одновременно выполнено следующее:

1. `uv sync` проходит на Linux.
2. `uv run ruff check .` проходит.
3. `uv run ruff format --check .` проходит.
4. `uv run ty check` проходит.
5. `uv run pytest` проходит.
6. `uv run gdis-loader` запускает GUI на Linux (при наличии tkinter/display).
7. GUI выбирает файлы и сохраняет/восстанавливает config.
8. `validate` корректно проверяет реальный тестовый комплект.
9. `update` создает новый `.xlsx`, не изменяя source calculator.
10. В `Данные` записываются только поля, разрешенные разделом 13.
11. Неоднозначные match не выбираются молча.
12. LHA не смешивается между различными пластами одной физической скважины.
13. Создается JSON report.
14. Есть тест, подтверждающий сохранность нетаргетных частей калькулятора.
15. При >100 строк таблица `tblData` расширяется, но другие листы не меняются; формируется warning о текущей расчетной емкости.
16. GitHub Windows workflow логически готов собрать `onedir` artifact без установленного Python на целевом ПК.
17. Реальные файлы `data/` не попали в git status как tracked.
18. Документация обновлена и не содержит ложных утверждений о закрытых бизнес-вопросах.

## Назначение проекта

`gdis_loader` — настольный загрузчик данных для Windows. Он читает несколько Excel/XLSM-файлов с исходными промысловыми данными и заполняет **только лист `Данные`** файла `GDIS_Rating_Calculator_FIXED.xlsx`.

Калькулятор рейтингования уже существует. На текущем этапе запрещено менять его методику, формулы, настройки, расчетные листы или внешний вид остальных листов.

## Технологический стек

- Python **3.14**.
- Управление Python и зависимостями: **uv**.
- Линтинг/форматирование: **ruff**.
- Проверка типов: **ty**.
- Тесты: **pytest**.
- Excel: **openpyxl** для чтения/анализа. Для безопасной записи допускается минимальная работа с OOXML через стандартную библиотеку (`zipfile`, `xml.etree.ElementTree`/совместимый XML-парсер), если это требуется для сохранения нетаргетных частей книги без изменений.
- GUI: **PySide6-Essentials** (`QtWidgets`/`QtCore`), без тяжёлых дополнительных GUI-модулей.
- Сборка Windows: **PyInstaller**, режим **onedir / standalone folder**, не `onefile`.
- Разработка: Linux. Целевая платформа: Windows 10/11 x64.
- Excel COM automation, LibreOffice automation и VBA не использовать.

## Важное правило Python 3.14

Синтаксис PEP 758 вида:

```python
except ValueError, TypeError:
    ...
```

для Python 3.14 является валидным. Не помечать его как синтаксическую ошибку и не «исправлять» добавлением скобок только ради совместимости со старыми версиями Python.

## Управление проектом

Использовать только `uv` для окружения и зависимостей. `uv.lock` должен храниться в Git; если lockfile отсутствует после изменения зависимостей, выполнить `uv lock`.

Основные команды:

```bash
uv sync
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
```

Перед завершением любой существенной задачи все четыре проверки должны проходить.

Не добавлять `requirements.txt`, Poetry, Pipenv, Conda или отдельные виртуальные окружения.

## Правила работы с данными

1. Каталог `data/` содержит реальные производственные файлы и полностью исключен из Git, кроме `data/README.md`.
2. Никогда не изменять исходные файлы в `data/`.
3. Не коммитить реальные `.xlsx`, `.xlsm`, `.docx`, `.pptx` из `data/`.
4. Все преобразования должны быть детерминированными и тестируемыми.
5. Если правило сопоставления неоднозначно — **не угадывать**. Оставить поле пустым/запись нерешенной и добавить диагностическое сообщение.
6. Нормализацию номеров скважин, пластов, дат и категориальных значений делать в отдельных чистых функциях.
7. Не смешивать чтение Excel, бизнес-логику и GUI в одном модуле.

## Главный принцип

Первая версия заполняет только те поля листа `Данные`, для которых правило однозначно следует из приложенных источников или явно зафиксировано в документации проекта.

Для остальных полей:

- не выводить искусственные значения `Нет`, `0`, пустую дату и т. п.;
- оставлять ячейку пустой;
- фиксировать причину в отчете загрузки;
- добавлять бизнес-вопрос в `docs/OPEN_QUESTIONS.md`, если вопрос еще не описан.

Актуальный набор подтвержденных ответов и временных решений описан в
`docs/CUSTOMER_DECISIONS.md`; этот документ заменяет устаревшие статусы ниже/в
предыдущей документации проекта.

## Целевой Excel-файл

Файл: `GDIS_Rating_Calculator_FIXED.xlsx`.

Целевой лист: `Данные`.

Из известных особенностей исходного файла:

- заголовки расположены в строке 6;
- данные начинаются со строки 7;
- таблица Excel называется `tblData`;
- исходный диапазон таблицы — `A6:Z106` (100 строк данных);
- колонок 26 (`A:Z`).

Загрузчик должен находить колонки по **тексту заголовков**, а не по жестко заданным номерам колонок.

Если записей больше 100, разрешено расширять **только лист `Данные` и `tblData`**. Остальные листы в первой версии не расширять и не редактировать. В отчете пользователю явно указать, если число загруженных строк превышает текущую расчетную емкость остальных листов калькулятора.

## Защита целевой книги

Требование пользователя: кроме листа `Данные` ничего не менять.

Обычный round-trip `openpyxl` может переписать служебные XML-части книги, удалить `calcChain`, преобразовать shared strings и удалить неподдерживаемые расширения условного форматирования. Поэтому нельзя считать «`load_workbook()` + `save()`» автоматически безопасным.

Обязательные требования:

1. До реализации writer создать тест round-trip/структурной целостности на реальном калькуляторе.
2. Проверить ZIP/OOXML-содержимое исходной и выходной книги.
3. Нетаргетные листы должны сохранять значения, формулы, размеры, merged cells, tables, charts, defined names и отношения.
4. Если чистый `openpyxl` не обеспечивает это, использовать openpyxl для чтения и формирования данных, а финальную запись сделать минимальным OOXML patch: заменить только XML листа `Данные` и связанный диапазон `tblData`, сохранив остальные ZIP entries исходной книги.
5. Никогда не перезаписывать исходный калькулятор без явного выбора пользователя. По умолчанию создавать новый файл результата.

## GUI

GUI маленький и утилитарный. Минимальный набор полей:

- Калькулятор `.xlsx`;
- Фонд скважин `.xlsx`;
- Сводная таблица ГДИ `.xlsx`;
- База ЛХА `.xlsm`;
- База по скважинам `.xlsx`;
- Суточный рапорт `.xlsm`;
- выходной файл `.xlsx` или каталог результата.

У каждого поля должна быть кнопка `Обзор...`, открывающая системный диалог выбора файла/пути.

Последние выбранные пути сохраняются в `config.toml` и автоматически восстанавливаются при следующем запуске.

Расположение `config.toml`:

- в frozen/PyInstaller-версии — рядом с `GDIS_DataLoader.exe`;
- при разработке — в корне репозитория.

Абсолютные пути пользователя нельзя зашивать в код или пакет.

GUI должен иметь:

- кнопку проверки входных файлов;
- кнопку запуска загрузки;
- понятный статус выполнения;
- итоговую краткую статистику;
- сообщения об ошибках без traceback для обычного пользователя;
- полный traceback только в лог-файле.

Долгие операции не должны «замораживать» окно: выполнять загрузку в worker thread, а UI обновлять безопасно через основной event loop.

Внизу главного окна используется штатный `QStatusBar`, который постоянно
показывает только `Версия MAJOR.MINOR` из `gdis_loader.__version__`; имя автора
в GUI не выводится. Справа от кнопок действий находится `QProgressBar`.
Каждый новый `validate`/`update` сбрасывает его в 0, получает только
GUI-independent progress checkpoints от service и достигает 100 только при
успехе. При ошибке значение не переводится в 100.

## Архитектура

Сохранять разделение ответственности примерно следующего уровня:

```text
src/gdis_loader/
  config.py
  cli.py
  gui/
  readers/
  domain/
  matching/
  transforms/
  validation/
  excel/
```

- `readers` — только чтение источников и первичная схема.
- `domain` — типы/модели предметной области.
- `matching` — идентификация скважины/ствола/пласта.
- `transforms` — вычисление целевых полей.
- `validation` — проверки источников и результата.
- `excel` — безопасная запись листа `Данные`.
- `gui` — только представление и координация, без бизнес-логики.

Не создавать «god module» и не помещать бизнес-логику в callbacks/slots Qt.

## Идентификация скважин

Простой JOIN по номеру запрещен.

Начальный ноль в числовом номере из фонда незначащий. Номер одной физической скважины может встречаться с разными lifecycle suffix и менять пласт во времени.

Основное правило из README исходных данных: при привязке учитывать комплексно номер скважины, пласт и дату; для актуального сочетания ориентироваться на последнюю релевантную дату ГДИ.

Нужны как минимум два понятия:

- `base_well_id` — физический корень, используемый только для lineage поиска;
- `target_well_id` — отдельная lifecycle identity, сохраняющая suffix (`ЗБС`, `ПВЛГ`, `МЗС` и неизвестные варианты).

`51 != 51_ЗБС`, `54 != 54_ПВЛГ`, `10403 != 10403_МЗС`. МЗС — отдельная история, не схлопывать его с материнской скважиной. Для fund без suffix связывать completion только через подтвержденную историю, месторождение, пласт и однозначную дату. LHA без suffix присоединять только при однозначном temporal lifecycle assignment. Не синтезировать ЗБС2/ЗБС3.

При нескольких равноценных кандидатах считать match неоднозначным и не выбирать случайно.

Для бизнес-логики загрузчика источником истины являются только:

## Логи и диагностический отчет

Каждый запуск должен формировать:

- краткий итог в GUI;
- текстовый лог;
- машиночитаемый отчет (JSON) рядом с выходным файлом или в `reports/`.

Минимальная статистика:

- количество скважин фонда;
- количество однозначно сопоставленных;
- количество неоднозначных;
- количество без ГДИ;
- количество без ЛХА;
- количество записанных строк;
- список незаполненных полей и причин;
- предупреждение о превышении 100 строк текущей расчетной емкости остальных листов.

Не включать в лог большие выгрузки или потенциально чувствительные данные без необходимости.

`DiagnosticIssue` хранит structured immutable `locations` из
`SourceLocation(file, sheet, cell)`. Reader warning/error, связанный с исходным
Excel, обязан указывать точный файл, лист и ячейку; для ошибок структуры книги
допустимы `sheet=null`/`cell=null`, если физической ячейки нет. JSON сохраняет
locations объектами, а text log выводит `file::sheet::cell`.

## Тесты

Тестировать не только happy path.

Обязательные классы тестов:

- нормализация номера скважины;
- ведущие нули;
- ЗБС/ПВЛГ/другие встреченные варианты;
- нормализация обозначений пластов (`ПК₁`, `ПК-1`, пробелы и т. п.);
- выбор последней записи по дате;
- неоднозначный match;
- отсутствие истории;
- чтение фонда из последнего датированного листа;
- чтение LHA с ошибочными/пустыми значениями;
- сохранение `0` как реального значения, а не как missing;
- config round-trip;
- writer не меняет нетаргетные листы;
- расширение `tblData` более чем на 100 строк;
- кириллица и пробелы в путях;
- Windows-style paths в config.

Integration tests, использующие реальные файлы `data/`, должны автоматически пропускаться, если файлов нет (например, в GitHub Actions).

Для CI создать небольшие синтетические fixtures, не содержащие реальных производственных данных.

## Стиль кода

- Полная типизация публичных функций.
- `pathlib.Path`, не ручная конкатенация путей.
- `dataclass(slots=True, frozen=True)` для подходящих неизменяемых domain-моделей.
- Явные исключения предметной области вместо голых `Exception`.
- Не использовать `except Exception: pass`.
- Не скрывать ошибки данных.
- Не применять pandas только ради нескольких Excel join/group операций; для текущего масштаба достаточно структур Python и openpyxl.
- Не усложнять архитектуру абстракциями без реальной необходимости.

## CI и релиз

CI должен запускаться как минимум на Linux и Windows и выполнять:

```bash
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
```

Release/build workflow на Windows:

1. устанавливает Python 3.14 через uv;
2. синхронизирует lockfile;
3. запускает проверки;
4. собирает PyInstaller `onedir` приложение `GDIS_DataLoader`;
5. архивирует каталог `dist/GDIS_DataLoader/` в ZIP;
6. публикует ZIP как GitHub Actions artifact.

Версии проекта и release tags строго двухкомпонентные: `MAJOR.MINOR` и
`vMAJOR.MINOR`; PATCH не используется. MINOR — глобально монотонный счетчик и
не сбрасывается при ручном изменении MAJOR. Workflow сначала вычисляет candidate,
передает версию без `v` в build script, генерирует временный build-version module
и проверяет её frozen smoke-test. После успешной сборки свободный tag создается
на exact `github.sha`; занятый tag приводит к failure, существующий tag нельзя
изменять, version-bump commit не создается. Release создается только после
успешного push в `main`; `workflow_dispatch` выполняет non-release build/test и
публикует только Actions artifact без повышения версии и без tag/release.

Никакого Python на целевом ПК требоваться не должно.

## Текущие подтвержденные решения заказчика

- Target scope этой итерации — только Береговое ЛУ; в workbook не добавлять
  колонку месторождения. Читатель `База по скважинам.xlsx` использует `БЛУ`;
  mapping других участков сохраняется в data model.
- `calculation_date` — локальная системная дата операции. Получить один раз в
  начале validate/update и передавать дальше явно.
- Начальный ноль числовой части номера незначащий. `base_well_id` является
  физическим корнем для lineage, а `target_well_id` сохраняет suffix.
  Материнская, ЗБС, ПВЛГ/перевод и МЗС — разные lifecycle identities. Не
  схлопывать МЗС; неизвестный suffix сохранять.
- Месяц/год в новой базе не превращать в синтетический день. `Дата запуска`
  записывается только с точностью DAY; MONTH/YEAR остаётся пустой с provenance.
- Подтвержденные классы ГДИ: ИД, ИД+КВД, КВД. Освоение, отдельные Pст/Pпл
  исключить. Не считать глубину условием валидности ГДИ.
- В текущих target rows временно писать `ГТМ = Нет`. ЛНД вычислять через
  confirmed tri-state, depth > 0 для выбранной GDI записи — глубинное
  исследование. Missing/invalid не превращать в `Нет`.
- Для одинаковых метрики/timestamp в ЛХА выбирать максимум валидных numeric
  значений, после collapse выбирать current/previous; выдавать INFO с provenance.
- Строки Берегового фонда пока не фильтровать по eligibility. Eligibility
  считать отдельно. `Недостаточно ГДИС` и остальные unresolved поля оставлять
  пустыми.
- АДД и `Техническая возможность` пока не удалять из workbook: target ячейки
  пустые, структурная миграция калькулятора — отдельная задача.
- Девять blockers перечислены в `docs/OPEN_QUESTIONS.md`; по ним запрещены
  fallback-значения и догадки.
